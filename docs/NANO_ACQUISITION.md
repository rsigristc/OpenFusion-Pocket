# Nano acquisition and initial power selection

Post-v2.0 correction included in v2.1. See [release notes](releases/v2.1.md) for the remaining live validation check.

## Diagnosis and Legacy reference

`InventoryWindow.NanoPacket` previously handled `REP_PC_NANO_CREATE_SUCC` solely by updating ownership and assigned skill. It did not implement the presentation or initial tuning mode. Existing summon animations and paid Nano Station tuning are separate flows and cannot replace that mode.

The reference is `NanoFreeTuningMode`, `CnGuiNanoFreeTuning`, `GameFrame`'s create-success handler and `cnMissionManager.CheckNanoFreeTuning` in the locally extracted Retrobution client. Legacy presents the acquired Nano, uses creation effect 705 and projectile rows 76/77, plays `call`, offers its three table-defined powers, submits `REQ_NANO_TUNE` and plays the chosen `skill1/2/3` only after success. Initial tuning uses the 44-byte request body without gathering the paid station's inventory requirements. Legacy also checks owned Nanos with skill zero so interrupted initial selection can resume.

The request's ten item slots must explicitly use the unused sentinel `-1`. A zero is a valid inventory slot. The [OpenFusion base server's setNanoSkill](https://github.com/OpenFusionProject/OpenFusion/blob/master/src/Nanos.cpp) checks these indices to distinguish the no-item initial flow from consumption logic; with all zero slots and insufficient Fusion Matter it can return without an acknowledgement after changing its bank. This is not proof of Retrobution's private implementation, but explains the first device test's missing ACK and establishes why zero-filled slots are incorrect here. The free initial request remains restricted locally to an owned, currently untuned Nano and its table-defined choices; station tuning is unchanged.

## Implementation

`InventoryWindow.NanoAcquisition.cs` queues award presentations on the main thread. It uses the original model, textures, animation clips, creation effect and projectile table through the existing resource/model/effect systems. The regular game camera is temporarily framed around the acquired model; its normal orbit variables remain untouched. No additional world camera or duplicate Nano inventory is created.

The primary-surface overlay uses Legacy's transparent `NanoPopUpNextNano_1` background (the actual `CnGuiNanoFreeTuning` binding, path ID 1487), NanoSkin bitmap fonts, original 356×460 popup/three-row geometry, letterboxing and Select buttons, with actual three power names, types, icons and descriptions from the Nano tables. This is distinct from My Stuff's framed/portrait popup. Touch/pointer clicks select a power; keyboard arrows/Enter are supported, and gamepad selection uses the existing menu pointer. Gamepad A is not separately processed as a second selection. Movement, combat, unrelated windows and DS commands are blocked for the modal presentation and restored on completion.

The shared bank changes only through the existing server packet handlers. A choice submits real Nano/tune IDs, blocks duplicate pending requests, handles rejection and waits for matching success before playing the selected skill and ending. Timeout does not automatically resend a potentially completed request; it offers a return to the game. An owned Nano whose skill is still zero is offered again from the next login bank or bank-subset packet. Tuned Nanos are excluded from that recovery. The offline training Nano remains under the existing tutorial flow. Death or travel interrupts presentation and requeues an unassigned power for when the world is usable again.

## Validation

`NanoAcquisitionRegressionChecks` exercises the actual inventory packet/queue path: award ownership, presentation/modal gates, malformed input, table-bound choice validation, request bytes, duplicate blocking, no optimistic skill/currency changes, rejection/retry, matching acknowledgement, completion and recovery from an ENTER bank containing both tuned and untuned Nanos.

`NanoAcquisitionAssetChecks` verifies the current server's Numbuh Two Nano model, skinned geometry/materials, original `call`, `stand1`, `skill1`, `skill2`, `skill3` clips, three real power descriptions and acquisition effect/projectile resources. Logs are under the ignored `Logs/nano-acquisition/` directory. The full configured regression suite and Android build also run these checks.

The first configured regression suite and Android packaging passed (`Logs/nano-acquisition/build.log`: 0 errors, 17 warnings). However, the first device test failed initial selection: request nano 2/tune 4 at 11:39:40.500 had no matching acknowledgement. The user also rejected its provisional UI. That version is superseded by the unused-slot sentinel correction and original Legacy presentation. The model facing direction was corrected after the captured device preview showed its back. Regression checks now explicitly assert all ten unused indices and required Legacy presentation fonts/assets.

The full suite passed again with the corrected sentinel (`build-legacy.log`, 0 errors/17 warnings). After verifying the exact transparent popup binding, the focused acquisition regression and final packaging passed (`build-final.log`, 0 errors/17 warnings). Final local APK: `Builds/OpenFusion-Pocket-nano-acquisition-preview.apk`, 116,973,723 bytes, SHA-256 `f62f33433d0953cf92c49f92f219d81e00e135799cbb15476b2f50014d292bb7`. The first final-install attempt could not connect to the old wireless ADB endpoint. After the user supplied the new connection endpoint, this APK installed successfully on AynThor without clearing app data, and PocketActivity was opened.

Final Android visual validation: the login bank reported `1:1,2:4` at 12:07:53.220 on 2026-10-25, confirming that the earlier Numbuh Two/F.A.S.T. F.E.E.T. choice persisted server-side despite its missing ACK. The read-only preview loaded the real model, creation effect, front-facing camera and original transparent/bitmap UI; `Logs/nano-acquisition/device-legacy.png` records the result. Continue restored the regular world/HUD (`device-restored.png`). The replay logs contain no tune request. The request file was consumed and no reward or equipment change was submitted by the preview.

A live initial-tuning ACK with the corrected unused-slot sentinels still needs verification when another owned, untuned Nano is acquired; the already assigned Numbuh Two skill was deliberately preserved. The client does not reset an assigned skill to replay the initial choice or replay mission rewards. Exact Legacy camera motion and the separate auto-equip/auto-summon behavior are not implemented by this correction.

The local `POCKET_INPUT_PREVIEW` build additionally supports a one-shot `nano-acquisition-preview.txt` in the app's own files directory containing an already owned, tuned Nano ID. It replays presentation read-only: normal initial-selection guards keep every power button disabled, and Continue returns to the world. It cannot grant a Nano, reset a skill or submit a tune for that already assigned Nano. The hook is excluded from normal release builds. This permits visual verification if the earlier server request persisted a skill despite the missing acknowledgement.
