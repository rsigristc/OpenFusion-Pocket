### Combat feedback audit — 2026-10-17 (local, unpublished)

Community feedback exposed client omissions, rather than sufficient evidence of a device-specific problem. Croc Pot appearance was disabled by PlayerAvatarFactory's default flag, despite the inventory icon path already interpreting the upper 16 bits of Opt. Visible equipment now enables the cosmetic IDs for supported categories 0–3 while retaining the original stat item/enchantment data. Appearance signatures trigger an equipment-model refresh for clothing changes without replacing the network holder or session; local locomotion, inventory pose and portrait references are refreshed. Remote equipment changes also include clothing and Opt-only style changes. Missing required local resources defer replacement; vehicle/special ride states defer local rebuilding. Generated clothing meshes/private materials are released by their owning avatar, with an ownership guard so portrait clones cannot destroy the live avatar's shared resources. Exact-balance Taros combination requests are now allowed. No combination or tuning was performed in live QA.

The local player had no death animation/respawn prompt equivalent to RemoteCombatAnim. PlayerLife and GameClient.Life now stop local locomotion/combat at authoritative zero HP, play die then death, and present a normal respawn request. XCom revival uses ePCRegenType.Xcom=1; Phoenix=3 and group Phoenix=4 are offered only with the appropriate server-derived condition/result. No HP or successful revival is synthesized: the client waits for REGEN_SUCC, permits a retry after timeout and checks connection state. Escape/game menu and full-screen panels remain accessible above the death flow. The server reply now restores HP, equipped Nano IDs and energy, bank stamina and Fusion Matter. Warp Away (type 5) is deliberately not used as the normal death request.

SkillResults adds bounded, target-checked decoding for local HP/stamina/condition/battery results from NPC skills, corruption, Nano skills and character/projectile attacks. In particular BatteryDrain (40B) does not share Damage's HP layout, and stamina/heal/buff result sizes differ. Truncated result lists are rejected before mutation. Ally heals, damage/debuff stamina and drained boosts now update the existing HUD data. Local Nano summoning/skill use is blocked while dead and world Nano models retire until health is restored. Server-confirmed Nano usage starts the active slot cooldown as well as linked cooldowns; the active-HUD cooldown is drawn directly after its own icon, including in DS. Passive Nano startup animations/effects and session cleanup were added. NPC skill animations are selected from the downloaded NPC/animation tables and held against locomotion; source/target effects reuse the existing effect/projectile renderer.

Protocol references checked: https://github.com/OpenFusionProject/OpenFusion/blob/master/src/core/Defines.hpp , https://github.com/OpenFusionProject/OpenFusion/blob/master/src/PlayerManager.cpp , https://github.com/OpenFusionProject/OpenFusion/blob/master/src/structs/1013.hpp and https://github.com/OpenFusionProject/OpenFusion/blob/master/src/Abilities.hpp . No synthetic online state or HP is introduced, and remote/network closure cannot be prevented by a client flag.

### Portrait render isolation, icon alpha and camera stability audit

The reported character/scene flicker exposed several unsafe rendering paths. Six portrait paths (character stage, AvatarPreview, NanoModelRt, own/other-player HUD portraits and NPC capture) used full RenderPipeline.StandardRequest; callers often assigned camera.targetTexture before the request and reset only that camera property afterwards. The installed URP 14 implementation restores its original target with Graphics.SetRenderTarget, so this pattern could leave the active drawing target pointing at the portrait. PreviewRender now centralizes these paths using UniversalRenderPipeline.SingleCameraRequest and restores the previous active target, camera target/aspect/clear/background, and object-fade global in finally, including failure. Preview cameras clear transparently, disable world fading only inside the render scope and opt out of postprocessing, shadows and extra color/depth copies. No full camera stack or main-camera viewport is deliberately rerendered. AvatarPreview targets now use 24-bit depth. Unity's [render-request API documentation](https://docs.unity.cn/2023.3/Documentation/ScriptReference/Rendering.RenderPipeline.StandardRequest.html) distinguishes full-stack StandardRequest from the single-camera request; the actual project package source (URP 14.0.12) was also inspected.

ActorAssembler replaced a prefab SkinnedMeshRenderer mesh and destroyed its previous sharedMesh, although that imported mesh belongs to DongBuilder's mesh cache. It now only replaces the reference; generated merged meshes/private materials continue to be released by their existing AvatarGeneratedAssets owner. This prevents preview/character construction from invalidating a borrowed cached mesh. No cache-owned mesh is freed by the assembler.

A local base icons bundle inspection found 1,852 DXT5 cosmetic icons with alpha, including 1,829 covering 0..255 and 21 covering 0..254. Thus black backgrounds must not be guessed away by a black color key or a global DXT1 transparency change. UnityConverters now keeps recognized interface icons in decoded RGBA32 instead of runtime mobile recompression, preserving source alpha/RGB. World-texture compression remains enabled. This is a scoped corrective path; it is not proof that every reported black icon was caused by the compressor. [Unity's compression API](https://docs.unity3d.com/ja/2022.3/ScriptReference/Texture2D.Compress.html) documents platform-dependent ETC/EAC conversion on Android.

The orbital camera snaps its final <2 mm smoothing tail to the target instead of repeatedly interpolating negligible differences. Eight bounded five-second stability reports record camera/player position spans, angular span and pad look values after entering the world. These help distinguish actual pose drift/physics from visual aliasing/render-state effects; the root cause of the user's distant-object shimmer and subjective shake still needs a stationary device comparison. Existing controller dead zones, visibility settings, mip limits and user antialiasing preferences remain unchanged.
